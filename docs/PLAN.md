# Skyjo Online — Plan

Living roadmap. The Product Owner (PO) agent may add, reorder, or cut milestones; every change to this file must be justified in the PR that makes it.

## Goal

A free, phone-first web game based on Skyjo's mechanics. Friends open a link, pick a display name, and play 2–8 players in real time. No accounts.

**Definition of done:** a public URL where 2–8 people on phones can create or join a room and play a full game to 100 points without errors. All rules are covered by tests, CI is green, and the README explains everything.

## Architecture

One npm package (no monorepo tooling). Four areas:

| Path                   | What                                                                                         | Runs on                  |
| ---------------------- | -------------------------------------------------------------------------------------------- | ------------------------ |
| `src/engine/`          | Pure, deterministic rules engine. No DOM, no Node APIs, no `Math.random`/`Date`. Seeded RNG. | client + server          |
| `src/client/`          | React app (online rooms; the local mode was removed in M6)                                   | browser                  |
| `src/server/room.ts`   | Platform-agnostic room: seats, protocol, reconnection, view projection                       | server                   |
| `src/server/worker.ts` | Cloudflare Worker + Durable Object adapter around `room.ts`                                  | Cloudflare               |
| `src/server/node.ts`   | Self-host adapter (Node + `ws`) around `room.ts`                                             | this computer (fallback) |
| `e2e/`                 | Playwright tests                                                                             | CI + local               |
| `scripts/gen-art.ts`   | Card/icon art generation via Gemini                                                          | local only               |

**Server is authoritative.** Clients send intents (`draw`, `swap`, ...). The server validates them with the engine, then sends each client a projected view. Face-down card values and deck order never leave the server.

**Hosting:** Cloudflare Workers free plan: static assets, one Worker, and one SQLite-backed Durable Object per room using hibernatable WebSockets. App and WebSocket share one origin. No credit card needed (verify at M4).

**Dev loop:** `@cloudflare/vite-plugin` runs the Worker and Durable Object inside the Vite dev server, so `npm run dev` is the whole stack.

### Tech choices and deviations from the brief

- **Workers static assets instead of Pages.** Same free tier, one deploy, one origin for app and WebSocket. Cloudflare now recommends this path for new projects.
- **Direct Durable Objects instead of PartyKit.** PartyKit runs on Durable Objects anyway; going direct removes a layer and a vendor.
- **Biome instead of ESLint + Prettier.** One dependency for lint and format.
- **The browser's Web Animations API** for card motion (FLIP in `src/client/motion.ts`). No animation library and no PixiJS. M5 tried `motion` (Framer Motion) and dropped it (PO, M5 review: this line still named it).
- **No router or state library.** `/r/:code` is parsed by hand; state is the server's room snapshot.
- **Hand-written message validation.** The protocol has fewer than 10 message types.
- **A hand-written service worker** instead of `vite-plugin-pwa`. `src/client/sw.js` is a template; a small plugin in `vite.config.ts` fills in the build's precache list and a per-build cache name. The manifest is the static `public/manifest.webmanifest` (PO, M5 review).
- **npm** (pnpm is not installed here).
- **Art via Gemini image generation.** `npm run art` reads `GEMINI_API_KEY` from the local `.env` (gitignored) and writes optimized WebP files that are committed. The key is never used in the client, CI, or repo. Generated: card back, face textures per value band, table background, logo, and PWA icons. Card numbers are rendered in CSS so they stay crisp. Prompts never mention Skyjo or imitate its official art.

## Multiplayer behavior

- **Create:** server issues a 5-character code from an unambiguous alphabet (no 0/O/1/I). Share link `/r/CODE` uses the Web Share API with a copy fallback.
- **Join:** display name, 1–16 characters. The lobby shows seats. The host (first seat) starts once 2–8 players have joined. If the host leaves the lobby, the next seat becomes host.
- **Identity:** a random token in `localStorage`, per room. Reconnecting with the same token reclaims the seat. Tokens are never broadcast.
- **Spectators:** anyone joining a full room (8) or a game in progress sees the public view. They can take a free seat in the lobby. Joining, leaving, and removing seats happen only in the lobby, so seat order always matches the game.
- **Reconnection:** the client auto-reconnects with backoff and shows a "Reconnecting…" banner. The server sends a full snapshot on reconnect. Seats are held for the whole game.
- **Turn clock and Auto-play (M8, replaces the 60 s stall guard):** each turn has 30 s from its start, and a draw always leaves at least 10 s to place. The opening flip has 30 s from the deal, shared by every seat still flipping. Online or offline, a seat whose time runs out gets the server's move (`autoMove`) and goes on Auto-play, which plays its turns a step at a time (draw 2 s into the turn, place 1.2 s later) until its player unticks it. A player can tick it too. The clock and Auto-play run only while a seated player is connected: another seat, on Auto-play or not, or the seat itself while it's on Auto-play; a player thinking alone has no clock. When nobody connected is playing by hand, Auto-play may turn over the last face-down card, so the round ends; the round summary waits for a tap on Next round (BUG-1, v2.1.1; it used to need a connected seat off Auto-play, and an all-auto table froze).
- **Next round:** the engine's `nextRound` carries no seat, so the room decides who may send it: the host advances from the round summary; if the host is disconnected, on Auto-play, or out of a knockout game (M17), any seated player can.
- **Persistence:** room state is written to Durable Object storage on every change, so eviction loses nothing. Idle rooms are deleted after 24 h via an alarm.
- **Rematch:** after game over, the host's **Play again** (anyone's, under the same rule as Next round) returns everyone to the lobby with the same seats. Late arrivals join there, and the host can remove offline (ghost) seats. Then the host starts. Each deal (every start and every new round) gets fresh CSPRNG entropy.

### M1 — Rules engine

**Acceptance:** every rule has a named test. Engine coverage ≥ 95% lines and branches. Engine imports nothing outside `src/engine`. Same seed plus same actions gives identical state.

### M4 — Deploy

Moved ahead of polish (the brief listed it last) so hosting risk is retired early and every later merge is testable on real phones.

**Acceptance:** the public URL works on a real phone. The smoke test passes against it. The Node fallback passes the same E2E locally, and `npm start` listens on `127.0.0.1` only. A test that passes only on retry fails its CI job.

### M8 — Turn timer and auto-play (user request, 2026-10-24) · v2.1.0 · ✅ shipped (PR #17)

One slow or absent player shouldn't stall the table. After 30 s with no move, the server starts playing for that seat, and keeps doing it until the player unticks **Auto-play**. The server is the authority on the clock; the client only displays it.

Decisions (PO, 2026-10-24), refined the same day with the UX expert's advice. Each says where it came from, and each has its reason:
- **The clock: 30 s per turn, with at least 10 s to place after drawing** (expert; replaces "each move restarts the clock"). The clock starts when the turn starts (a new `RoomData.turnSince`). Drawing doesn't restart it, but the place deadline is never less than 10 s after the draw, so a turn takes at most 40 s. _Reason: the bar drains once per turn, which matches the user's "30 seconds", and the grace keeps the drawn-card decision fair._
- **The flip phase is covered too: 30 s from the deal** (PO). The clock covers both flips and is shared by every seat that hasn't flipped; other players' flips don't restart it. The round summary, game over and the lobby have no timer. _Reason: one absent player would otherwise hold up the deal for everyone (the stall guard already covers the flip phase today). The expert's report was split on this, so the PO decided._
- **Every phone shows the same server deadline** (expert). `RoomView.wait` becomes a list of `{ seat, inMs, reason: "timer" | "offline" | "auto" }`, one entry per waited-on seat (there are several in the flip phase). The client draws each countdown as one CSS animation with a negative `animation-delay`, not one render per second. _Reason: every phone agrees, and the bar drains smoothly at no cost._
- **The acting player** (expert; replaces "no clock for the first 20 s"). A 4 px bar drains above your grid for the whole turn, with no number. At 10 s left it turns orange, the pill reads "Your turn · 10", and screen readers hear "10 seconds left" once (`role=status`). At 5 s it turns red, and the phone vibrates once (where `navigator.vibrate` exists) and plays one soft tick (respecting mute and the silent switch). The vibration ignores mute, like the turn-start buzz: mute is the 🔊 switch, and a muted player needs the warning most (PO, PR #17 review). _Reason: the bar is always visible but never pushy, and the warning is a single nudge._
- **Everyone else, players and spectators** (expert). The active panel's gold border becomes a draining ring, and the number shows only in the last 10 s. For an offline seat, the prompt line says so ("Cris is offline · auto-play in 24 s").
- **The auto-move gets smarter, and the stall guard uses it too** (expert; replaces "`autoMove` unchanged"):
  - It draws from the deck.
  - If the drawn card is lower than your highest face-up card, it swaps the drawn card in there.
  - Otherwise it discards the drawn card and flips the first face-down card in reading order. The exception is your last face-down card: flipping that would end the round, so it swaps into your highest face-up card instead. It never ends the round while another legal move exists.
  - In the initial flip, it flips the first two face-down cards.

  _Reason: today's move (`room.ts:341-350`) fills the grid in reading order and ends the round for an absent player, who then likely gets doubled (R12)._
- **You can watch auto turns** (expert; replaces "one move every 1.5 s"). An auto-play seat draws 2 s after its turn begins, and places 1.2 s later (PO, PR #17 review; was 1.5 s and 700 ms, see the round-1 decisions below). Each step is its own broadcast. Today `tick()` plays the whole turn and broadcasts once (`room.ts:245-247`), so nobody sees the draw. _Reason: everyone sees the drawn card (R6) and each card flight._
- **The Auto-play checkbox lives in one place: the row right above your grid** (expert and PO, reconciled).
  - Off: it is a quiet "Auto-play" checkbox in your grid's header row, so you can tick it before stepping away.
  - On: that row becomes a persistent "Auto-play is on" bar holding the same checkbox, at least 44 px.
  - The server ticks it when your time runs out, and only you can untick it.
  - While it's on, tapping your cards, the deck or the discard does nothing; the bar shakes and the phone vibrates, pointing at the checkbox. No tap is silently swallowed.
  - Unticking during your turn gives you a fresh 30 s.
  - If you come back while it's on, the bar reads "Auto-play was on while you were away".
  - Labels: en "Auto-play", es "Juego automático", pt "Jogada automática".

  _Reason: there is one control, and ticking it yourself is what lets E2E test auto-play without waiting 30 s._
- **What others see** (expert): 🤖 on the seat's panel and in the round summary, and the pill reads "Beto · auto".
- **Offline seats get the same 30 s, then go on auto-play** (expert and PO). Today every turn of an offline seat waits a fresh 60 s (`room.ts:304-306`, reset at `:336`), which at 8 seats is about 10 minutes per round. Delete `STALL_MS` and that deadline rule. Keep `canStall` and the `STALE_MS` presence check.
- **A table only plays itself while someone is really there** (PO, Security row). The timer and auto-play run only while at least one connected seat is not on auto-play. _Reason: auto turns are moves the server makes without any client message, each costing alarm runs and row writes. A room full of auto seats must not play all day on the free plan's quota._ Since v2.0.4 every row must be charged to whoever causes it, when it's written (SEC-11, `spend` in `worker.ts`): charge each auto turn's alarm to the IPs with a live socket in the room, like a presence check, and keep `holdRooms` at ≥ 14 h. The turn clock also retires v2.0.4's stall-guard quirk, where a seat that drops mid-turn is moved 60 s after its turn began. **Superseded by BUG-1 (v2.1.1):** a table where everyone is on Auto-play froze in live play. Since SEC-11 charges alarms to connected IPs, auto seats now keep playing while any seated player is connected, and the round summary is where they stop.
- **A host on auto-play counts as away,** so any seated player may lead (next round, rematch, start).
- **Spectators** see everything but have no checkbox and don't affect the timer.
- **No host setting to turn the timer off** (AGENTS: no speculative config). Revisit if the user asks.
- **Wake Lock** (UX-6, folded in). Request `navigator.wakeLock` during a game, request it again on `visibilitychange`, and release it on Home. _Reason: at 6–8 seats the wait between your turns is longer than iOS's 30 s auto-lock. A locked phone goes stale after 45 s, and then auto-play would take over._
- **Cards keep their size** (UX-12, folded in). The offline and countdown text lives in the prompt line, never in a row of its own. The Portuguese discard prompt gets shorter so it fits on 2 lines at 360 px. _Reason: M8 rewrites exactly that text, which today shrinks your cards from 64 to 55 px mid-turn._
- **The pill pops once per turn** (UX-10, folded in). Its key drops the phase (`Table.tsx:151`). _Reason: M8 rewrites the pill._
- **Protocol:**
  - a client message `{ t: "auto", on: boolean }` that applies only to the sender's seat;
  - `Seat.auto`, persisted;
  - `SeatView.auto`;
  - `RoomData.turnSince`;
  - the `wait` list described above.
- Lands the After-M6 items marked "→ M8".
- Update § Multiplayer behavior (stall guard), `AGENTS.md` (online flow) and the README's how-to-play.

**How it was built (author, PR #26).**
- **The curve.** `path()` in `motion.ts` is pure and unit-tested. It samples the flight at fixed times, with the travel following `cubic-bezier(0.3,0,0.2,1)`, so the lift, lean, arc and settle sit at the times in the spec. The acceptance's "at 50%" is then 50% of the time. Each frame is one `transform`.

- **The back face** is a `::before` with the card back. - **Stacking.** A card in motion gets `data-motion` (z-index 2), and the card going in gets "in" (z-index 3). The grid and the opponents' minis lost their `perspective: 700px`, which made them stacking contexts that trapped their cards under the piles. Each turn now carries its own `perspective(6w)`. Discard mode isolates the grid for its glows (UX-18).
- **Sounds** use the timing of the animations that actually started: `useFlights` returns it, by element key. A card's sound is placed so that its loudest moment (draw 130 ms, place 160, discard 210 into the file) falls when the card hits home, at the bottom of its settle (0.94 of its flight). That is within ±30 ms of both touching down (0.88) and the end, whichever "landing" means. Flip sounds follow the order the cards really turn. "Your turn" waits for the last card to land, and a column's chime for its card to reach the pile; before, they had stayed at a fixed 250 ms, ahead of the slower landings (review, PR #26). The summary hold and the game-over sound also come from that timing: 600 ms after the last animation ends, instead of a guessed flip length.

### Security hardening (SEC) (user request, 2026-10-24) · one patch each

**Goal:** a bot can't take the service down or ruin other players' games on the free plan. The threats include creating rooms in bulk, flooding sockets, guessing room codes, spamming joins or spectators, griefing games in progress, and burning the Cloudflare free plan's daily quotas (Worker and Durable Object requests, duration, storage writes). What exists today: per-IP room creation is rate-limited (`ROOM_CREATION`), each socket is capped at 120 messages per 10 s, frames over 1000 characters are rejected, and empty rooms expire after 10 min.
1. **Audit.** A security engineer agent probes a **local** server only, never the live URL: abusing the live URL would burn the same free quotas the game runs on. It returns findings SEC-1, SEC-2, …, each with a severity, a proposed fix, an acceptance criterion, and whether it needs a Cloudflare dashboard action.
2. **Triage.** The PO puts each finding in the table below, in the same shape as the UX triage: a severity, an effort (S / M / L), a verdict (**do**, **fold** into an open item, **defer**, or **decline**), and a one-line reason. The PO also marks whether it needs the user. Triage is a docs-only PR, and it can share one PR with the UX triage.
   - **Critical:** one cheap client can take the service down for everyone, or use up a daily free-plan quota.
   - **High:** one client can ruin other people's games or rooms, or take one room down.
   - **Medium:** the attack needs sustained effort or many clients, or does limited damage.
   - **Low:** defense in depth.
3. **Order.** Critical and high SEC findings may go ahead of any milestone that hasn't started, the same way UX blockers do; the PR that changes the order says why. Medium and low findings are ordered by value for effort alongside the UX items. Ordering never interrupts an open PR: it is still one PR at a time.
4. **Ship.** One small PR per finding, or per tight group. Each ships under its SEC id on a branch `sec<N>-<slug>` (for example `sec3-no-op-writes`), not under a milestone number, so the M numbers above don't shift. It goes through the normal loop (review → PR → PO) with the release checklist; a fix is a patch version. Build it test-first: room limits are unit-tested on the injected clock, and Worker routes are tested through the fetch handler with fake bindings.
5. **Acceptance per item:** the finding's reproduction, run again against a local server, no longer works, and a test fails without the fix. The PR also says how much each blocked attempt still costs on the free plan (requests, storage writes), and confirms that legitimate play is unchanged: the full E2E suite stays green, and no limit trips for 8 friends who share one IP behind a home router.
6. **Needs the user: Cloudflare dashboard changes.** The PO and authors can't make dashboard changes or create secrets. Examples are a WAF or rate-limiting rule, a Turnstile site key and secret, and usage notifications. Each becomes a "Needs the user" item, listed below and in the report to the user, with exact steps: the dashboard path, every field value, the secret's name if one is needed (set by the user with `wrangler secret put` or as a GitHub secret, never committed), and how to verify the change worked. The code half of such a fix merges only after the user confirms the step, or it must work unchanged without it.
7. **Done** when every finding is shipped, deferred or declined, and every "needs the user" step is done or declined by the user.

**Audit (2026-10-24).** It was measured against a local Node server; the live site was not load-tested. The engineer found these already well defended: the 8-seat cap; name sanitizing (no XSS); 122-bit tokens, with `seat` set by the server; the 1000-character frame cap and the 120 messages per 10 s flood limit; empty and idle room cleanup; pings answered without waking the object; and path traversal on Node.

The PO checked the engineer's numbers against the Cloudflare docs:
- [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#daily-requests) — 100,000 requests a day on the Workers Free plan, reset at 00:00 UTC.
- [Static assets billing](https://developers.cloudflare.com/workers/static-assets/billing-and-limitations/) — `run_worker_first` paths always invoke the Worker and get a 429 once the quota is gone, while static assets are free and keep loading.
- [Durable Objects pricing](https://developers.cloudflare.com/durable-objects/platform/pricing/) covers four points:
  - 100,000 requests a day, including WebSocket messages and alarm runs. Incoming messages are billed at 20:1, and outgoing messages are free.
  - 13,000 GB-s of duration a day. An object that is idle and eligible for hibernation isn't billed for duration.
  - 100,000 rows written a day.
  - Each `setAlarm()` is billed as one row written.

### BUG-1 — Everyone on Auto-play freezes the table (user report, 2026-10-25) · v2.1.1 · ✅ shipped (PR #21)

**Report.** In live room `8WTHE`, both players were in the room. The other player's time ran out, so the server switched their Auto-play on; then the user ticked Auto-play himself. From then on nobody's turn advanced, while both phones said "Auto-play is playing for you".

**Root cause (PO, read-only on `main` 2c69751).** This is M8's quota rule working as written, and it is the wrong product behavior.
- `canStall` (`room.ts:493-495`) runs a seat's clock and its Auto-play only while _another_ seat is connected **and not on Auto-play**. With every seat on Auto-play, `clocks` is empty and `tick` plays nothing.
- **The spectator view** (one socket, no seat, no action) showed round 1, other's turn in the draw phase, the pill "other · auto", 🤖 on both seats, Juan offline, other connected, and no clock ring.
- **A second path needs no tick from anyone.** In the opening flip, `tick` (`room.ts:400-409`) collects every due seat _before_ switching any of them to Auto-play. If both players are present and neither flips within 30 s, both go on Auto-play in the same call, and the table freezes after their first flips.
- **Not the cause:** a stuck clock, a missed alarm, or SEC-9's ping-only return. And Auto-play turning on for a present player after 30 s is M8's design.

**Why the rule can go (PO).** M8 added it so that auto turns, which no client message pays for, couldn't burn the free plan's rows. Since SEC-11 (v2.0.4), every alarm is charged to the `MESSAGES` budget of each IP with a live socket in the room, so a table of auto seats pays for itself. An all-auto table plays about one turn per 3.2 s. That is about 4 budget units per turn, roughly 75 a minute per connected IP, which is under the 0.75 × 120 margin M8 measured. So no new worst case opens up.

There is a second guard the old rule hid: `autoMove` never flips a seat's last face-down card while the round isn't ending. That protects an absent player among humans, but it means a round where everyone is on Auto-play would never end.

**Decision (PO): keep playing, finish the round, and stop at the summary.** This is not a "paused" notice: both players asked for Auto-play, and the help text promises that it plays for you.
- **Who counts as there.** A seat's clock runs while another seated player is connected, whether or not they are on Auto-play. A seat on Auto-play also keeps playing while its own player is connected. Spectators don't count, and neither will M17's out players. Nobody connected means nothing plays (nobody pays).
- **Ending the round.** When no connected seat is off Auto-play, `autoMove` may flip the last face-down card, so the round can end. With a human playing by hand, the old protection stays.
- **Where it stops.** The round summary still waits for a tap on Next round, which any seated player may give while the host is on Auto-play. So a table of auto seats costs one round at most per human tap, and auto seats stay on for the next round until someone unticks.
- **Priority: next, ahead of SEC-9 and M17,** as a hotfix (patch 2.1.1). Real players hit it in live games, the fix is effort S, and when this was triaged (04:10 UTC) SEC-9's branch had no commits, so nothing open is interrupted. SEC-9 moves to 2.1.2. It isn't folded into SEC-9, so that the security PR keeps one scope and the PO reviews each change on its own.
- **Workaround until it ships:** one player unticks Auto-play, and the table moves again.

**Acceptance:**
- Room unit tests on the injected clock:
  - With 2 seats both on Auto-play and both connected, the current seat draws at +2 s and places 1.2 s later, and the round reaches the summary.
  - With both on Auto-play, A connected and B offline, the table still plays.
  - With both on Auto-play and nobody connected, nothing plays, and `nextAlarm` schedules no auto step.
  - A lone connected player off Auto-play, on their own turn with everyone else offline, gets no clock (unchanged).
  - In the opening flip, with both present, if neither flips for 30 s, both go on Auto-play, both flip twice, and the first turn starts.
  - With a connected player off Auto-play, auto seats still never flip their last face-down card before the round is ending (unchanged).
- `autoMove` unit tests:
  - It flips the last face-down card when the round may end.
  - In a simulation of 1,000 seeded all-auto tables of 2–8 seats, every round ends.
- The SEC-11 charge test: an all-auto 2-seat table charges each connected IP ≤ 0.75 of its `MESSAGES` budget per minute.

### M17 — Play until one is left (knockout) (user request, 2026-10-24) · v2.2.0 · ✅ shipped (PR #24)

The user asked for a game option, **"Play until one is left"**, and approved the rule and the edge cases below after a walkthrough. It is numbered M17 because M9–M16 were already planned, but it ships before them (see § Queue after M7).

**The rule (R16, an option, off by default):**
- The host ticks **Play until one is left** in the lobby before starting. When it is off, R14 is unchanged.
- Scores still count only at the end of each round. Nobody goes out mid-round.
- After each round, every player with a total ≥ 100 is **out**. They keep their seat, name and total, and they watch the rest of the game. No cards are dealt to them.
- The players still under 100 play the next round, and only they get cards. When two are left, they play head to head.
- The game ends after a round in which at most one player is still under 100:
  - if **one** is under 100, that player wins;
  - if **none** are (everyone still in crossed 100 in the same round), the lowest total among them wins, and ties share the win.

**Edge cases (approved by the user):**
- **R3 and R4:** only active players flip. The start player has the highest 2 flipped cards among them; ties go to the lowest seat, as now.
- **R5:** turn order skips players who are out.
- **R10:** "every other player gets one more turn" means every other active player.
- **R12:** the ender's doubling is compared only against the players in that round.
- **M8:** a player who is out has no turn, so no clock entry and no auto-play.
  - Going out clears that seat's auto-play.
  - Out seats count like spectators (BUG-1): they don't keep the clock or Auto-play running, and they don't count when deciding whether anyone is still playing by hand. A room test checks both, and that a lone connected spectator keeps nothing running either: no test pins that yet (PO, PR #21).
- **The host going out** still leads (Next round, Rematch), **and so may anyone seated** (PO ruling, PR #24): the same rule as for a host on Auto-play or offline.
  - _Reason: the screen stays on during a game, so a knocked-out host who puts the phone down still looks connected. Every later round summary would wait on them, and the players still in would have no way to go on. Going out also ends Auto-play, which was the other way to let someone else lead._
  - _Cost: once the host is out, whoever taps Next round or Play again first moves the table on. At game over the host is usually out, so anyone may send the table back to the lobby. That is the behavior friends already get when the host is on Auto-play._
- **An active player who drops:** as now; the timer and auto-play keep the table moving.
- **Final ranking:**
  - the winner, or the tied winners, are 1st;
  - everyone else ranks by the round they went out, later ranking higher;
  - players who went out in the same round rank by lower total;
  - the summary shows "Out in round N".
- **An out player's view:** their seat shows "Out · watching", and they see the table the way a spectator does.
- **Rematch:** everyone is back in, and the lobby keeps the checkbox as it was.

**Design (PO):**
- **Engine:**
  - `createGame(names, seed, options?)`, with `options = { knockout?: boolean }` kept in `GameState`, so the next deal and the scoring see it.
  - Each player gains `out: number | null`: the round they went out.
  - The ranking is a pure engine function, so the client never ranks (M13's sorted summary reuses it).
  - The engine stays pure: it imports only `./…`, with no `Date` and no `Math.random`.
- **View:**
  - `GameView` gains `knockout` and each player's `out`, both public.
  - An out player's grid is empty: no cards, so nothing to hide. Hidden information is unchanged.
- **Lobby:**
  - The checkbox can be changed only by whoever may lead (the host, or anyone while the host is away, as for Start), and only in the lobby.
  - Everyone in the lobby sees its state, so everyone knows the rule before the deal, and a stand-in leader starts with the same setting.

### M21 — Throw things at your friends (user request, 2026-10-27) · v2.5.0

The user asked for a feature "like Parchís": throw bombs, beers or donkeys at other players, and make it funny. This is the deferred "quick reactions" idea (§ After M6), now the user's call. The PO had a research agent and a UX expert scope it before building.

**Research (summary).** Online Parchís and Ludo apps let you tap an opponent's avatar and throw from a small tray; the whole table sees the item fly from thrower to target and land with a gag. What players complain about is spam aimed at whoever is thinking, so every big game ended up with a mute (Clash Royale added one 3 months after refusing to). What keeps it funny: rare, seen by everyone, one friendly item in the mix, and it never blocks play. 🫏 (Emoji 15, 2022) shows as an empty box on many LatAm Android 12–13 phones, so the art is our own inline SVG.

**UX (summary).** Two taps, inside a sheet the player opened on purpose: tap an opponent (their full-size grid, which already existed), then an item in a row under it. No items on the table, so no accidental throws. Flights are fixed elements over the cards (z 8, under the summary's dim) that never take a tap. A target in an 8-player strip scrolled out of view gets the throw at the strip's edge; the strip never scrolls for a throw. The thrower is always visible (the item starts at their name).

**Scope.**
- Six items: bomb ("Boom!"), beer ("Cheers!"), donkey ("Hee-haw!", hops instead of flying), tomato ("Splat!"), flip-flop ("Bonk!", "¡Chanclazo!" in Spanish) and kiss ("Mwah!"), each with a gag bubble in en, es and pt, coloured bits on impact and a sound (`boom`, `splat`, `bray`, `kiss`, generated with ffmpeg at −23 dB mean like `last.mp3`).
- Whoever is hit gets a vibration of its own per item, unlike the turn buzz, the nudge or the Auto-play buzz. It is skipped in that player's last 10 s, so the nudge stays the only buzz then.
- A **Throws** switch next to the items, remembered in `localStorage`: off, you see and hear no throws and can't throw.
- Seated players throw, those who are out too (R16); spectators only watch. Not at yourself. No flights over the summary.
- Reduced motion: the item fades in where it lands, with its bubble and sound; nothing flies or shakes.

**Server and security.** One new entry point, the `toss` message. It writes no row: the room keeps the throw in memory and returns `"view"`. Its bounds:
- one throw per seat every 3 s (`TOSS_MS`; a throw too soon returns `"none"`);
- one `MESSAGES` unit like any message (120 a minute per IP);
- the per-socket flood limit.

The client sends it without a `seq`, so a throw never holds up a move.

**Acceptance.**
- Unit tests (`room.test.ts`): a throw shows in every view for 2 s and saves nothing. No throws in the lobby, from a spectator, at yourself or at a seat that isn't there. 3 s per seat, and only for that seat. Parsing rejects bad items and non-integer targets.
- E2E (`e2e/toss.spec.ts`):
  - the items are only in an opponent's sheet, 6 buttons of at least 44 × 44, at 2 and 8 players, with no sideways scroll, and spectators get none;
  - a throw lands on your name bar and lets taps through, a second one at the same target is dropped, and the switch turns throws off across a reload;
  - between two phones (Pixel): Ben sees Ana's donkey and his phone gets its vibration, Ana's items rest 3 s, and Ana's move right after a throw goes through.
- The release checklist, with README images refreshed: the "Tap an opponent" still now shows the items.

## Process

**One PR at a time.** The next PR starts only after the previous one merges: its branch is cut from the `main` that includes it. That way every milestone builds on the shipped game and every PO review sees a single change (user request, 2026-10-24). Docs-only PRs, such as plan or triage edits, follow the same rule but don't bump the version. CI's CHANGELOG check passes because the current version already has its section, and the release job skips a version that is already released.

Per milestone:
1. Branch `m<N>-<slug>` from `main`. Build test-first for engine and room code.
2. Run the `superpowers:requesting-code-review` review, then fix its findings.
3. CI green.
4. Open a PR with a summary, mobile screenshots (Playwright, committed under `docs/screenshots/m<N>/`), and test results. Bump the `package.json` version, add its `CHANGELOG.md` section, and refresh the README (rerun `npm run shots:readme` if the UI changed). Merging to `main` then deploys and publishes the GitHub Release.
5. Dispatch the PO agent: a fresh subagent that has not seen the implementation. It reads this plan and the PR, runs the game locally, plays it through Playwright at a mobile viewport, and scores the rubric. It then posts review comments and either merges or requests specific changes. It may edit this plan, with justification in the PR.
6. At most 3 PO review rounds per PR. If still not approved, stop and summarize the open issues for the user.

**GitHub constraint.** Author and PO both act as `jack1590`, and GitHub forbids approving or requesting changes on your own PR. So the PO posts a comment review whose first line is `PO VERDICT: APPROVE` or `PO VERDICT: CHANGES REQUESTED`, adds inline comments through the API, and merges with `gh pr merge --squash` once CI is green. Branch protection therefore requires 0 approvals but does require CI.

### PO rubric

Each criterion is scored 1–5, or N/A when the milestone has no surface for it (multiplayer in M1–M2, for example).

| Criterion             | 5 means                                                                                                                                                                                          |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Rules correctness     | Every rule R1–R16 behaves as specified in play and in tests                                                                                                                                      |
| Mobile UX             | One-handed portrait play, clear turn state, ≥ 44 px targets, no dead ends                                                                                                                        |
| Visual polish         | Original, cohesive art; readable cards; smooth, purposeful motion                                                                                                                                |
| Multiplayer stability | No desyncs; reload and network drop recover; no leaked hidden info                                                                                                                               |
| Security              | A scripted client can't take the service down, use up a free-plan quota, get into rooms by guessing, or disrupt another room's game; every limit is tested; no open critical or high SEC finding |
| Code health           | Small, tested, readable; matches `AGENTS.md`; no dead code                                                                                                                                       |
| Delivery health       | PR CI wall time ≤ 3 min; no flaky, retried or timed-out jobs; every CI job has `timeout-minutes`; `npm run e2e` runs locally in ≤ 2 min                                                          |
| Game feel             | Sound, haptics and motion make every move feel physical; any player count is readable at a glance; friends would want a rematch                                                                  |

Security is scored on any PR that touches the server, the protocol or a route, and is N/A otherwise. The PO lists each new entry point (a message type, an HTTP route, an alarm, a storage write) with the limit that bounds it. An entry point with no bound is a blocking defect.

The PO measures delivery health on every review, using `gh run view --json jobs` for wall and per-job times and a timed local `npm run e2e`, and reports the numbers with the score.

**Approve when** no applicable criterion is below 3, no blocking defect is open, CI is green, and the release checklist is done: version bumped, CHANGELOG section matches the PR, README text and images show the current game.
